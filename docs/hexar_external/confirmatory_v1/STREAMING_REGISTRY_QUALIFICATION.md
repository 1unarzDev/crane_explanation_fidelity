# Streaming phase registry development qualification

The compatible `registry_shards_v1.py` bounds each saved shard but retains all phase payloads while building and verifying a complete registry. At the conditional N=3,072 planning scale, initial judge requests project to roughly 1.8 GiB before Python-object copies. The new `streaming_registry_shards_v1.py` writes/verifies one bounded shard at a time and retains only index metadata across the full phase. It does not change a method, prompt, endpoint, judge, response cap, unique-request rule or scientific N.

Input is a strictly increasing stream of opaque job IDs. Final stage admission must separately verify complete identities against the frozen episode/battery schedule. The builder rejects unordered/duplicate jobs, oversized whole requests and oversized indices. Generation begins with a durable no-provider claim; a failure retains the partial namespace and never publishes a complete index or permits reuse. It uses the existing exact greedy byte/job partition and canonical registry/index formats. Incremental canonical hashing is checked against the prior complete-object hash, including Unicode payloads. Existing compatible bundle verification and single-attempt journals remain supported.

The streaming executor verifies the complete phase before initializing an independently admitted root, then reads only the requested payload shard. It repeats independent root/index/shard admission before calls and retains the existing closed/crash dispositions without reissue. The callback interface is qualification plumbing, not scientific authorization. Production H1/provider/stage chronology admission is not supplied by this module.

The fixed synthetic capacity screen is declared before execution: **73,728 synthetic jobs**, 8 MiB maximum shard bytes, 128 jobs per shard, a 512 MiB peak-RSS screen and 300-second build-plus-verification screen. It repeats the already-inspected 144 initial-judge request templates from the completed v3 development run, under distinct sorted synthetic IDs. This corresponds only to a request-count capacity example of 24 × 3,072; it does not acquire 3,072 episodes or choose N. No backend is constructed, no method/judge output is generated, and no significance calculation is performed. The exact declaration, source hashes and result are retained in `development_streaming_capacity_v1`.

The screen runs once as a standalone process after its declaration is committed. Every stream generation and shard is immutable; failures remain retained. The complete payload bank follows local large-artifact storage policy, with the index/report hashes recording every shard's bytes and identity. Qualified storage/archive publication must precede any final production freeze.

Thirteen focused tests cover exact byte compatibility, global schedule preservation, partial generation rejection, immutable roots, raw tamper/extra-file detection, denied admission, normal closed-attempt reuse, interrupted claims and pre-provider rejection of a changed requested shard. These tests and capacity evidence do not certify an actual provider, stage chronology or scientific activation. Final confirmation admission remains independently fail-closed.
