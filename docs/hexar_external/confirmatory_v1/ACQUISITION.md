# Fresh TIAGo/Nav2 acquisition qualification

The target is an **adapted simulated HEXAR external-validation benchmark**, with one independently generated simulated robot episode as the statistical unit. All eighteen original HEXAR recordings are development-exposed. Replays, edits, masks and new answers from them remain development evidence.

## Selected stack and provenance

The closest first-party public stack identified is PAL Robotics' ROS 2 Humble TIAGo simulation with Gazebo Classic and Navigation 2, Ubuntu Jammy, public simulation, differential-drive base and `arm_type:=no-arm`. The [official simulation README](https://github.com/pal-robotics/tiago_simulation/tree/43cb13f383216c4a36210374ebffe220f6c9469d) explicitly documents public Gazebo, Nav2, and combined bringup. It recommends Cyclone DDS for public simulation reliability. The [official workspace recipe](https://github.com/pal-robotics/tiago_tutorials/blob/humble-devel/tiago_public.repos) enumerates the PAL packages. We resolved every recipe branch to a full commit in `analysis/hexar_external/acquisition/tiago_public.lock.repos`; tracking branches will not be silently refreshed.

The Dockerfile uses a content-pinned official ROS Humble base. ROS/Gazebo binary dependencies must also be captured in the resulting image's `binary-packages.lock` and immutable image digest before acquisition freeze. A Dockerfile alone is not a qualified runtime. Gazebo Classic/Humble is selected for proximity to the released ROS 2 navigation interface and first-party PAL support. End-of-life status of Gazebo Classic motivates pinning the complete image and removing external network dependencies at episode execution.

## Candidate process requiring runtime qualification

Every episode starts a fresh isolated simulator and fresh Nav2/AMCL processes. No process, map mutation, controller history, AMCL particle state or ROS message cache survives into another episode. Run containers use isolated DDS domains and Gazebo masters. A prospective master seed derives per-episode Gazebo/scenario/start-goal seeds with distinct namespace fields; actual simulator command-line seed application must be verified, not inferred from the plan. Starts and goals are sampled from a prechecked collision-free frame in the selected map, with fixed distance limits and randomized headings. Simulator reset, initial pose, lifecycle activation and localization settling occur before the episode starts.

The episode begins at an actual accepted navigation goal and ends at terminal action result or the prospectively fixed acquisition timeout. Record raw `/clock`, `/tf`, `/tf_static`, `/scan`, odometry, AMCL covariance, action status/feedback, actual Nav2 `/rosout`, controller commands, and explicit task bookkeeping. Retain infrastructure topics for technical qualification. Only the frozen visible-evidence interface is released to the methods. Hidden family/intervention/seed/truth metadata stays outside method and judge packets.

Family generators must retain all six families:

- `success`: unmodified navigation in the static map;
- `obstacle`: a physically simulated static obstruction in the intended route;
- `dynamic_env`: physically simulated moving obstruction with bounded, independently seeded trajectories;
- `localization`: a precommitted AMCL initialization/sensor perturbation, retaining actual estimated covariance rather than writing synthetic uncertainty diagnostics;
- `manual_joystick`: actual simulated command arbitration enters manual priority, publishes its observed state, and preempts autonomous navigation according to implemented policy;
- `charging`: implemented simulated charging/interlock state preempts navigation according to policy and publishes its state.

A family name never supplies a diagnostic log. Charging and joystick state publishers may represent a simulated supervisor only if they govern the actual command/action policy. They must be documented as simulated adaptation rather than physical TIAGo hardware observations. Nav2/AMCL log statements must be captured from the real software; they must not be fabricated to match development fixtures. The no-arm benchmark tests navigation explanation, not physical fetching or manipulation. Task wrappers must report only actually executed navigation stages and action results.

## Candidate technical validity and reserve policy

Validity depends on acquisition integrity and correct scenario execution, not explanation quality or whether navigation succeeds. Candidate predicates include fresh process identities and new bag content; applied and unique seeds; correct image/configuration hashes; active Nav2 lifecycle; accepted goal; advancing simulation clock; required sensor/action/message streams; valid bag metadata and monotone episode boundaries; verified requested intervention delivery; and no recorder loss/corruption beyond frozen limits. Valid navigation failure, slow navigation, inability to plan, abort and cancellation remain valid outcomes. In particular, a valid `success`-family episode that fails to navigate cannot be discarded simply because it failed.

Exact thresholds and timeouts are unresolved until measured during development. Freeze them before confirmation. Invalid runs are preserved with outcome-blind reason codes and hashes. Replacements use the next preallocated independent seed within the same family, never a replay; do not inspect method outputs or judge labels to choose replacements. Exhausted reserves terminate acquisition with incomplete status, without extending N opportunistically. Final N and reserves are selected only after qualification and power sensitivity audit.

## Release gates

Acquisition qualification requires actual raw episodes covering every family, process-reset/seed checks, repeatability-versus-independence checks, successful bag parsing, intervention audit and topic/interface compatibility. The raw cohort can then be acquired and sealed under frozen rules before H1 resolves. Semantic H2 execution still requires the fixed-sequence H1 rejection gate. An unresolved alpha gate does not prohibit development or raw acquisition engineering.
