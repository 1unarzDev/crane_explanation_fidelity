## Concrete provenance and packaging gaps

**Durable restoration is not established by a hash manifest.** The existing `publication_manifest.json` lists 35 local assets and `v2/archive_manifest.json` lists 327; this audit verified every listed file exists and every recorded hash still matches. `archive_v3.py` currently inventories v2/v3 file hashes but does not create a byte archive or record transfer/storage receipts. `v3/archive_manifest.json` is not yet present. Final handoff must retain actual ignored call/cache/event bytes in an immutable private archive or coordinator-managed object store and record a checked restore/location receipt. Keep raw-data redistribution policy separate from private preservation. A lost workspace cannot be reconstructed from SHA-256 alone.

The final restoration bundle also needs the v1 publication-manifest assets (native dispatch trace, parity snapshot and initial extraction/calls), source-data manifest, dependency lock and code commit. `archive_v3.py` scans v2/v3 only, so it must be paired with that earlier manifest and the repository snapshot/commands; do not imply its file list alone covers native or initial-tranche provenance. Re-downloadable upstream inputs remain pinned, but provider calls and clock traces are not regenerated exactly by downloading HEXAR.

**Public redistribution remains unresolved, not automatically prohibited local analysis.** Do not publish bags, extracted events or raw source-bearing call payloads under package Apache-2.0 assumptions. For any public source adaptation, preserve applicable package LICENSE/notices and modification attribution. Public artifacts can instead cite upstream downloads and report hashes/analysis summaries; review derived packet/answer payload exposure separately before publication. This audit does not grant dataset or speech/asset rights.

**Runtime provenance can be made more exact without pretending hosted weights are immutable.** The scoped environment currently runs Python **3.14.7**, but the requirements lock alone does not encode that interpreter and the documentation's generic `python -m venv` command can select another version. Retain interpreter/OS and Codex CLI version or executable identity with the final archive, along with model request/settings and pinned container image. Hosted weight/tokenizer/backend identity remains unavailable; mark that as a lasting reproducibility limitation rather than fabricating an artifact hash or claiming exact historical phi4 reproduction.

**Exposure accounting should be cumulative.** The initial `audit/split.json` lists only `bagfile_6_1.bag` as inspected development input. Later documents and development manifests cover all six repetition-1 recordings and both full-query and fresh q1 answer versions. Add a new cumulative exposure record or clearly link later manifests without rewriting the initial declaration. Preserve reserved semantic noninspection until activation. Public historical answers/scenario truths were necessarily accessible for category A; opaque handles do not remove potential model familiarity or establish unseen-family transfer.

**Native parity limits must survive final shortening.** Later deterministic replay uses original bag receipt timestamps rather than native traced callback receipt times; the tested equivalence is under declared clock instrumentation. There is no full lifecycle/selector/action scheduling parity or historical replay-clock recovery, and only the initial manual recording has native parity. Additional family/mask correctness is deterministic boundary testing, not another native replay result. Four development recordings show float-conversion timestamp inversions, and final charging indicators occur after selected task windows. Claims must stay bounded to latest state and logs; do not turn these records into measured inhibition, geometry or delay mechanisms.

## Unsupported causal-assertion reporting limitation

Read-only inspection of `report_v2.py::score` confirms that the existing `unsupported_physical_cause_rate` selects only atoms whose abstraction level is `specific_physical_cause`. Software/action causal links and task-outcome causal explanations preserved at other abstraction levels are excluded. `unsupported_material_rate` includes broader factual claims and therefore mixes causal and noncausal assertions. Neither measure is a distinct rate for **all material unsupported causal assertions**, as requested by the handoff. Report both using their actual names and state this coverage limitation; do not rename unsupported material as causal risk or infer a complete causal-assertion benefit from it.

The two measures also treat unresolved annotations differently: `unsupported_material` excludes `UNINTERPRETABLE` from its observed flag and reports fixed-denominator uncertainty bounds separately, whereas the specific-physical-cause flag treats every label other than `SUPPORTED_BY_VISIBLE_EVIDENCE`, including `UNINTERPRETABLE`, as positive. Its rate is calculated over annotated jobs and lacks a corresponding dedicated unresolved/technical bound. Thus that measure is a conservative non-supported physical-cause flag, not an adjudicated unsupported-cause rate under identical missingness handling. Preserve and disclose this distinction when interpreting the frozen report.

If complete causal-role reporting is required, construct it as a separately governed secondary reporting task with a prospectively specified semantic causal-role definition, qualification and explicit unresolved dispositions. Do not modify inventories, primary endpoint, methods or frozen rules retrospectively, and do not silently reclassify existing abstraction levels as equivalent to causal roles. This audit inspected scoring code only; it did not inspect new comparative labels or outputs.
