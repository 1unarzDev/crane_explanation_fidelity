# Rendering v3 candidate — owned handles, narrow launch scope

This additive engineering candidate leaves rendering v2, collectors, existing declarations and failed attempts unchanged. No live compositor, player, container or collector is operated. Tests use mocks and disposable ordinary Python subprocesses. It makes no physics/sensing equivalence, scientific causal-repair or final-platform promotion claim.

The supplied Hyprland v0.56.2 source supports Lua rule handles: `hl.workspace_rule` returns a workspace-rule object with `set_enabled`/`is_enabled`; `hl.window_rule` returns a window-rule object with analogous methods. A unique named window rule is registered once, and a uniquely scoped workspace rule is created. Cleanup disables only those retained handles with checked `is_enabled()==false` assertions, releases their Lua globals, removes the owned output and verifies its absence. It **does not reload global configuration**. No supported deletion API was established, so disabled rule objects may remain in compositor registries until normal configuration refresh; the implementation honestly uses disabling rather than invented removal. Unique nonce rule/output/global names avoid replacing a known user rule. Workspace namespace collisions are checked before mutations.

The previous class-wide CRANE rule is deliberately unavailable. A real launch requires an independently established pre-mapping class `CRANE-owned-<32 lowercase hex digits>`, absent from existing client state. The rule matches only that nonce class. After launch, exactly one mapped matching client must occupy the owned workspace/monitor and report a PID in the new launch session/process group with start time no earlier than the observed leader. This adds genuine OS ownership evidence to class/placement. Another same-class PID outside the session cannot qualify. The nonce class contract prevents a rule from governing every unrelated CRANE instance, but is not authentication against a malicious process deliberately impersonating the nonce.

**Current Unity/collector integration is not ready.** The existing player reports `CRANE.x86_64`; no verified player option to assign a nonce class was found or invented. V3 refuses that ordinary class before compositor mutation or launch. The current collector is not changed to use this wrapper. A successor needs a validated exclusive app-class mechanism or another source-supported PID-scoped pre-mapping rule/launcher interface before live integration. Merely passing `--expected-class` cannot make a player change its class. This narrower safe behavior is preferable to advertising isolation that a generic class rule cannot provide. Probe-only mode needs no window rule or player and tests only owned output/workspace/FPS setup/cleanup; this work did not run it live.

Every mutating hyprctl eval/output operation requires exact `ok` success. Public source strings such as `Name already taken`, `output not found`, `no backend replied to the request` or `eval is only supported with the lua config manager` are rejected even with process exit zero. FPS setup uses Lua and exact getoption readback at 60. Cleanup independently attempts child-group termination, owned window-rule disabling, owned workspace-rule disabling, owned output removal and original-FPS restoration/readback. Failure of an earlier stage cannot skip later stages. Original errors and each cleanup error are recorded; incomplete cleanup fails the wrapper instead of silently returning collection success.

The CLI requires a fresh audit path. An exclusive intent is written before setup; the final structured audit records placement/FPS/session identity, cleanup statuses/errors, primary failure and return code. It is an operational lifecycle record, not a scientific declaration. A SIGTERM handler raises an interruption so ordinary finally cleanup runs; exceptions including KeyboardInterrupt are retained and re-raised after cleanup. SIGKILL, host death, unavailable compositor or disk failure cannot be guaranteed recoverable. If launch session identity cannot be obtained, unverified signaling is refused and cleanup failure is explicit. The final audit write/print may itself fail under I/O errors; no universal durability guarantee is claimed.

Linux `/proc` start-time/session/group readback gates termination. Cleanup runs even if the immediate launcher already exited, so surviving original process-group descendants receive TERM and, if needed, KILL. Each group signal is preceded by membership/session/start-time checks, and the wrapper refuses its own process group or an identity change. Zombie descendants are not running and are excluded. This is a practical process-group boundary: escaped sessions, container-owned processes and PID visibility differences are outside its authority. It neither touches containers nor claims process-name matching can safely find escaped children. Linux `/proc` readback and killpg are not an atomic primitive; an extreme membership-change race remains a limitation. A production integration should explicitly qualify lifecycle/namespace behavior, and stronger per-process pidfd/cgroup isolation may be warranted if groups can escape.

The original FPS is restored and verified, but FPS is a global compositor option while active. Concurrent user edits can be overwritten by restoring the original value, and multiple render wrappers require external single-worker serialization. Adding/removing outputs can cause compositor-internal workspace reassociation. Disabling owned rules avoids the prior blanket reload but does not prove arbitrary user compositor state or focus is unchanged. No complete-state preservation claim is made. Successful initial placement also does not guarantee no later manual window migration; a production collector could retain periodic ownership/placement observations prospectively. These limitations remain before any confirmation infrastructure release.

Validation: 11 new tests plus five retained v2 tests pass (**16 total**). Coverage includes exact operation-error rejection, inactive workspace tolerance, owned-handle disabling without reload, independent cleanup despite disabling/removal failures, restored FPS readback, refusing current broad class before mutation, exact client session ownership, changed-group signal refusal and mocked interrupted launch cleanup. A disposable Python parent exits while its sleeping child remains in the launch group; the real Linux lifecycle test confirms surviving-descendant cleanup without any Unity/container activity. Tests never launch a collector or claim deployed compositor equivalence.
