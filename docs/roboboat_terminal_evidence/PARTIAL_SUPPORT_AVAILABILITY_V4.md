# Full-method support with exact partial availability: development v4

This additive bridge lets reviewed available answers receive qualified support annotation while preserving every original response and method slot whose extraction/review/judgment is unavailable. It never treats a deadline or missing annotation as an explanation-quality failure, deletes an inconvenient answer, retries an extraction or changes the complete-supported-answer endpoint. Existing v1/v2/v3 sources, tests, declarations and live calls remain byte-identical.

## Prospective availability lock

`run_roboboat_full_population_support_v4.py snapshot --bank BANK --availability NEW.json` mechanically inventories every original blind text. Each of its two extraction returns, attempt receipt and source review is recorded by exact path/hash or an explicit observed-missing path. Return identities must match the original text, opaque key and A/B slot. Available extraction means both returns are structurally valid and the exact source review declares complete faithful assertion coverage with matching two-pass hashes and nonempty verbatim source spans. A claimed complete review cannot hide a missing or invalid return.

The selection is exhaustive and label-free: all eligible texts are selected. Paired valid extraction without a complete faithful review is **unreviewed source exists**; failed/missing/pending extraction returns are **extraction return unavailable**. Reasons and original source/review bytes are retained. No support label, complete-answer score, method comparison or family effect determines inclusion. A text reused across evidence contexts retains every original join; one shared extraction does not create independent N or permit merging different evidence contexts.

Availability verification binds the original blind bank, join, accounting and genuine inventory declaration, and every present receipt/return/review. Snapshot creation and preparation exhaustively check the live bank: an existing review cannot masquerade as missing. Preparation checks this live classification again immediately before writing the support declaration, whose hash binding freezes the snapshot. An arrival during preparation requires a fresh snapshot/preparation namespace, rather than silently changing eligibility.

After preparation, run/release reconstruct the mechanical classification using only the snapshot's retained paths and verify every retained hash. Previously absent paths may appear while other extraction/review workers continue; those later files are invisible to this namespace and the originally unavailable answer slots remain unresolved `[0,1]`. No dynamic promotion occurs. Existing bound bytes still cannot be overwritten, including retained attempt receipts; active writers must respect that immutability. This permits partial development support without stopping independent workers or waiting for all missing paths to remain absent. Later arrivals can enter only a new prospective availability namespace. Later namespaces do not authorize reissuing old extraction calls or revising old declarations; cross-namespace annotation reuse is not automatically implemented by this bridge.

## Preparation and qualified execution

The v4 `prepare` phase takes the usual bank/response/root/output/declaration arguments plus the explicit `--availability` snapshot. It accepts authentic full inventory v2 or v3 according to the real schema, rather than fabricating a legacy declaration. It reuses the existing full-method admission, deterministic full-B4 provenance/regeneration, original B2 single-call raw provider receipt checks, qualified prompts/schemas, material workflow v3 and immutable bank dependencies.

Every original source answer/provenance is admitted and preserved in the evaluator join/accounting before selection. Only eligible texts produce blind annotation packets; unavailable joins carry `support_packet_id: null`, their exact availability reason and unresolved `[0,1]` bounds. Response-generation failures and truly missing methods remain in the original ledger and full snapshot denominator. No method outputs/evaluator joins are staged to explanation generation. The support declaration binds the new adapters/tests and transitive runtime closure, including unchanged qualified execution and safe transport dependencies.

The v4 `run` phase verifies that exact lock again, uses the authentic qualified **600-second** safe annotation override, at most two concurrent packets, two independent passes, disagreement-only adjudication and zero quality retry. Existing support terminals and unresolved intents retain the inherited one-shot behavior. This version issues no extraction/provider call itself during preparation. A fresh deadline arm is not a retroactive extension of any prior extraction attempt.

## Release with unresolved slots

`summarize_roboboat_full_population_support_v4.py` accepts genuine v4 declarations and preserves their exact original response entries, registry, original response accounting, mechanical availability selection and declared packet set. Every completed available annotation must receive the full exact-source/citation review binding both raw passes, agreement and final decisions. An omitted completed citation review blocks release; a completed final cannot be hidden behind a missing or failed terminal. The inherited narrowly specified secondary abstraction-label exception remains supporting-only.

A missing/pending support terminal or genuine technical support failure without completed final decisions yields unresolved `[0,1]`, preserving why and observed missing annotation paths. An unreviewed existing answer or unavailable extraction also yields unresolved `[0,1]`, with no fabricated semantic score. Other reviewed complete annotations can still be released. Whole-answer/materiality/unit/limitation labels, all atomic labels, raw agreement and supporting abstraction issues remain visible for available judgments.

Explicitly unavailable primary decisions can be retained under citation-review status `PRIMARY_DECISIONS_UNAVAILABLE_RETAINED`, with complete source review, both valid raw passes/final binding, and exactly the missing/null primary inventory named in `unresolved_decision_keys`. Available labels still pass unchanged inventory/endpoint validation. Such an answer remains wholly unresolved `[0,1]` even when another supplied field is false; this conservative development sensitivity does not interpret partial judgments as failure. A clean PASS cannot conceal null primary judgments, and invented/extra/misidentified primary keys are rejected.

Method totals use every declared condition-method slot. A panel of 48 conditions has 48 B2 and 48 B4 slots regardless of availability. Unknowns contribute 0 to adverse and 1 to favorable success totals; paired differences retain corresponding bounds. Counts distinguish all answer-status reasons and call them unresolved slots. Complete two-variant/three-level geometry summaries are emitted only for complete source-reviewed paired decisions; partial geometries stay separate. Slots, masks, review passes and text reuse add no N. There is no significance test, inferential activation, alpha consumption or confirmatory/replication observation count.

## Limits and engineering validation

Missingness may depend on response length, complexity or extraction difficulty. The lock prevents selective omission but does not make missingness random or resolve the comparative effect. Bound-width and missingness-pattern reporting remain essential; this bridge does not justify replacing missing judgments with failed answers or claiming superiority from the reviewed subset. Source/citation completeness is project agent-assisted, not independent human validation. Fresh late-review snapshots and annotation reuse need an explicit future declaration; the current namespace never changes retrospectively.

All execution in this engineering task uses construction packets, mocked provider receipts, synthetic extraction/source reviews and synthetic annotation labels. No actual source bank was prepared, no real answer was inspected, no provider/support call was made, and no empirical study score was released. Validation covers preparation-time exhaustive selection and forgery rejection, late return/review/attempt arrivals without dynamic promotion, immutable reviewed dependencies, availability classification, shared text/context joins, genuine v2/v3 admission, raw receipt/source/review tampering, late path arrival, full citation gates, technical/primary missingness bounds, 48-condition denominator preservation and unchanged qualified 600-second execution behavior.


Final focused validation: 47 construction tests passed across v4 support/release, unchanged v2 support/release and qualified deadline v2. Both new modules passed Python compilation. All five deliverable files are additive; no frozen source/test bytes or live worker files were edited.
