# Prospective RoboBoat baseline interface candidate — development v1

This document proposes a new development comparison before any new primary calls. It reads no answer banks or comparative outcomes, freezes no method/test/N, and does not promote a primary baseline. Existing full-B4/Astra-high declarations and the historical certificate/renderer interfaces remain unchanged. Their baseline can run the entire permitted treatment, and their outputs remain **method-reuse sensitivities**. A future restricted architectural comparison must use a new name, namespace, source manifest and untouched response generation; it cannot retrospectively describe those older interfaces differently.

The paper defines B2 as the strongest fair repository-aware tool-enabled agent, B3 as deterministic diagnostic contracts/planning without complete final-claim verification, and B4 as maximal-supported planning, claim-ID-aware realization and final removal/generalization of unsupported clauses (`paper/main.tex`, prospective evidence-intervention subsection). It explicitly permits governed source/configuration access appropriate to each declared interface and forbids deliberately weakening B2. `COMPLETE_ANSWER_DESIGN_V1.md` preserves identical evidence, exact robot source/configuration and executable primitive computations, while distinguishing a new architecture comparison from the existing wholesale method-reuse condition. `FULL_RESPONSE_INTERFACE_V2.md` records that the current reuse B2 receives the full adapter, catalog, planner, realizer and inherited helper closure.

There are two different questions. An architecture comparison asks whether CRANE's explicit planning/claim-bound realization/verification improves complete supported answers over a strong agent using the same robot evidence, task semantics and diagnostic computations. An unrestricted reuse comparison asks whether an agent given that complete implemented architecture performs better or worse when allowed to invoke it, copy its text or adapt it. Both are useful, and a tie in reuse is scientifically legitimate. Calling the first comparison superiority over the strongest unrestricted repository agent would overstate its boundary. “Strongest fair” must be qualified by the **prospectively declared architectural interface**, not interpreted as whichever restrictions produce the largest B4 effect.

## Proposed strong architecture interface

Candidate name: **B2 shared-marine-diagnostics agent**. It retains every previously available marine temporal helper, including the legacy deterministic renderer. This is a deliberately strong incremental architecture comparison. It does not force an agent to rederive goal error, hull geometry, temporal support or partial sampled compliance unaided, and does not remove an existing answer-producing helper merely because a template might be competitive. Its interpretation is full CRANE integration versus an agent with shared temporal diagnosis and legacy presentation, rather than full CRANE versus an agent lacking executable diagnostics.

The distinction is executable treatment orchestration, not public physical facts or freedom to reason. B2 may inspect source, run all supplied helpers, choose the renderer verbatim, construct its own claims/plans/checks, use generic reflection or verification, implement additional arithmetic and generate any supported wording. There is no instruction banning evidence calibration, structured reasoning, self-checks, claim IDs of its own, or a reconstruction of ideas from public knowledge. It does not receive the installed full-CRANE orchestration/catalog/planner/realizer source or its precomputed outputs in this candidate workspace. Giving those exact components back defines the retained reuse condition.

| Resource | Proposed B2 architecture access | B4 access / parity requirement |
|---|---|---|
| Evidence packet and question | Identical bytes at the same L0–L2 condition; all permitted observations, provenance and missingness | Identical bytes; no richer stream or unmasked condition |
| Public task specification | Identical goal, hull/berth geometry, dwell policy, tolerances/uncertainty, contact requirement, clocks, frames and evidence limitations; same general explanation objective | Identical public specification; B4 may encode it in treatment contracts |
| Effective robot configuration | Exact YAML, hash, node/plugin-scoped readback and interpretation basis; declared versus measured/consumed configuration distinguished | Identical accessible bytes and provenance |
| Robot implementation | Exact relevant deployed navigation/action/goal-checker, command and odometry/frame/clock sources, version-bound and audited to contain no episode truth | Same common source bundle; unavailable deployed source is disclosed symmetrically |
| Shared numerical/temporal diagnostics | The unchanged five-file certificate/renderer closure below, plus any prospectively added common numerical/input-validity helpers | Same versions and numerical results; no private extra measurement stream |
| General tools | Shell/read/search, Python, math/json/hash/YAML and predeclared numerical libraries; runnable supplied scripts; temporary scratch computations | Same permitted environment where applicable; B4 remains its declared deterministic implementation |
| Full CRANE treatment modules | Not staged for this architecture candidate; no B4 intermediate/final outputs | B4-specific catalog, maximal diagnosis/planning, claim-bound realization, verification/repair permitted |
| Evaluator references, judge labels, expected episode answers, annotation inventories and hidden simulator truth | Excluded | Excluded |

The common marine source list is exact at the path level and must be hash-snapshotted before new calls:

- `analysis/roboboat_temporal_certificate.py`
- `analysis/roboboat_temporal_certificate_v2.py`
- `analysis/roboboat_temporal_renderer_v2.py`
- `analysis/roboboat_temporal_renderer_v3.py`
- `analysis/roboboat_temporal_renderer_v4.py`

Retain this full runnable local import closure and preserve relative module paths. B2 may call `scoped_config`, `observation`, `measure`, `validate_packet`, `certificate` and `render`, and the renderer versions. The certificate already provides support states, complete sampled-window checks, component witnesses, timestamp/crossing brackets, task aggregation, contact completeness reasoning, result-adjacent measurements, radial-error growth and explicit unidentified-cause scope. The renderer already communicates positive partial sampled compliance. These are substantive diagnostic aids, not merely a calculator; their presence and baseline usage must be reported. Excluding only the treatment while retaining these aids is more defensible than silently calling them forbidden contracts.

The treatment source boundary excludes staging `analysis/roboboat_full_crane_v1.py`, `analysis/roboboat_full_crane_v2.py`, `configs/roboboat_claim_contracts_v2_development.json`, `analysis/maximal_supported_diagnosis.py`, `analysis/realize_evidence_calibrated_explanation.py`, `analysis/evidence_calibration.py` and their treatment-specific import closure. `analysis/evidence_calibration_io.py` mixes generic serialization with ontology handling; its entire source need not be supplied merely to grant hashing/JSON parity, which stdlib already provides. A genuinely required generic operation should be shared through a reviewed neutral helper with identical behavior, not withheld inside a treatment-only module. A future treatment version must declare its complete closure rather than assuming this illustrative current path list remains exhaustive.

The scientific reason for excluding those implemented components is that maximal claim-contract planning and verified realization are the intervention under evaluation, matching the B3/B4 definitions. Their **public task facts** must not be excluded with their implementation. Any currently private prerequisite in `build_inputs`—supported sample clocks, reference alignment, fixture-timeout interpretation, finite configuration checks, physical requirements or scope assumptions—must appear in the shared public task/source specification or an identically callable input-validity/numerical helper before calls. Otherwise B4 would have privileged semantic knowledge or admissibility checks and the proposed comparison would not be ready. Do not ship the ontology's required-claim selection, source-to-approved-claim mapping or treatment-specific repair logic disguised as a primitive; retain those in reuse sensitivity.

The robot source bundle needs a concrete deployed-version manifest before implementation, not a blanket copy of this research checkout. Relevant repository candidates include `CraneROSNavigationState.cs`, `ROSOmniXCommand.cs`, `ROSThruster.cs`, `Odom.cs` and clock/frame dependencies where they govern the delivered stream, together with exact installed Nav2 goal-checker/action/controller sources and active configuration. Their inclusion depends on the actual deployed profile, with transitive source resolution and opaque versions/hash bindings. Public implementation may describe general mechanisms but cannot reveal an episode-specific injected condition. Do not stage `RoboBoatDockingEvaluator.cs`, evaluator-only geometry/state, scene-instance parameters, raw simulator summaries or independent reference answerability code as robot evidence merely because source is readable in the coordinator repository. Provide public task requirements separately. If an implementation file combines legitimate robot semantics and hidden evaluator access, use a prospectively audited neutral public contract/excerpt identically for both methods and disclose the omitted scope; no result-dependent edits.

A fact-only agent interface excluding certificate aggregation/rendering may be useful as a **supporting component ablation**, with a new declared namespace and complete math access. It is not automatically the strongest architecture baseline. If legacy certificate/renderer access gives an agent more complete answers, the proposed stronger shared-diagnostics candidate must remain eligible; one cannot select the fact-only condition because it increases B4-minus-B2 advantage. Conversely, an agent that uses legacy output verbatim remains a valid baseline answer, not a failure to engage with the task.

## Prompt, tool and resource strength

The baseline prompt should state the same public objective as B4: reported action outcome; supported physical outcome at the specified scope; decisive available measurement/interval witness or evidence limitation; positive partial sampled compliance when established; and necessary causal/temporal/contact limits. It must permit supported extra information and useful partial diagnoses. It may explicitly recommend examining/running the provided certificate/renderer and checking the final answer against the packet. It must not require speculative prose, ban copying a valid template, conceal the correct dwell policy or impose verbose output that creates extra unsupported claims. The general success criteria can be disclosed to both methods; case-specific required-unit inventories, judge spans and gold labels cannot.

Tool-enabled means executable computation actually works. The current transport uses an ephemeral workspace and `read-only` CLI sandbox. Before any successor calls, test that inline Python, supplied helper imports and subprocesses run, and that a writable isolated scratch directory is available if baseline-generated scripts or output files are advertised. Do not promise writes that the sandbox denies. Source/evidence files remain immutable, while temporary scratch can support unrestricted local checking within the declared deadline. Neither method receives research/home mounts, prior responses, answers from other evidence levels, judge tools or evaluator artifacts. Internet/external retrieval is unnecessary for the frozen packet and repository comparison; available local dependencies and provider communication should be bound and explained rather than silently removed for B2 alone.

`gpt-6-astra/high` is the current reuse setting, not established as the strongest future feasible setting by this document. Challenge it prospectively on independent development configurations at a genuinely provider-supported higher reasoning effort. Proposed finite candidate set, contingent on capability verification: Astra high and xhigh, plus the currently supported newest general-agent competitor (candidate `gpt-6.1-sol` high/xhigh). Record exact model IDs/version availability and reasoning-effort acceptance before calls; unsupported settings remain recorded technical incompatibilities and must not be reported as weaker answers. Do not substitute a new alias or unsupported effort silently. A still higher supported effort can be added through a new pre-call development declaration if there is a substantive reason to doubt the first challenge establishes a strong operating point. Highest effort is not automatically highest accuracy, and no model is chosen from its unfavorable contrast with B4.

Original calls retain their original 300-second deadline and zero retries. For a **new** development resource comparison, predeclare both 300- and 600-second per-entry deadline arms on the selected effort settings, using fresh response identities and the same complete development configuration panel. The longer deadline must apply consistently across settings being compared; it cannot be a response-dependent extension or retry. Retain timeout/provider/schema failures separately, with all successful deterministic B4 outputs, valid B2 outputs and method-call accounting. Predeclare failure treatment for future inference; do not silently drop failed calls or equate transport failure with semantic failure. A high-effort baseline that repeatedly times out indicates an operating-point problem, not evidence that its completed explanations are poor. If 600 seconds remains inadequate, inspect infrastructure and declare a fresh feasible arm before calls rather than forcing that limitation into an explanation-quality advantage.

No arbitrary equality of B2 and B4 model tokens or runtime is implied: current B4 has zero model calls and closed-template realization. A scientifically strong baseline should receive sufficient feasible resources to finish, while resource use is reported as a separate tradeoff. Bind token/context/output caps, available tool libraries and concurrency/provider capacity; avoid artificial caps on baseline inspection or diagnostics. Two isolated workers are a current orchestration choice, not a statistical N cap. Higher effort, more source inspection and longer timeouts increase cost/latency and may expose provider limits. The transport currently retains latency and records monetary cost as unknown; report missing billing measurements rather than claiming equal spend. Token/cost telemetry must be collected where available before a cost-normalized claim. No cost-normalized superiority is selected here.

## Actionable predeclared development comparison

Prepare an independently generated, balanced six-family development panel with all two-variant/L0–L2 entries, selected by technical capture validity before responses and without answer-based scenario filtering. Publish immutable method-interface/prompt/source/settings/deadline manifests and the baseline selection rule before any calls. The arms should cover:

1. The **existing unchanged full-method reuse interface**, keeping all full CRANE and legacy helper access as the strongest method-reuse sensitivity. New model/resource challenges require their own fresh declarations; old calls keep their identities.
2. The proposed **shared-marine-diagnostics architecture interface**, retaining the five-file helper/renderer closure and shared public robot/task source. Run the declared model/effort/resource challenges without imposing restrictions on agent-created reasoning or verification.
3. Optional **fact-only agent component ablation**, clearly secondary and never automatically promoted over a stronger eligible shared-diagnostics agent.
4. The fixed full-B4 method on the same visible packets, with its deterministic realization status, source closure and any platform/validation repairs prospectively recorded. No B4 outputs are staged in baseline workspaces.

For later baseline setting selection, use baseline complete-supported-answer quality **itself**, call completion, annotation reliability and useful information coverage on independent development data. Do not select by the largest B4-minus-baseline effect, by which interface loses, or by favorable-family subsets. Where feasible, use one development panel to screen and a fresh panel to validate the setting, carrying the full candidate list and all failures forward. A predeclared rule could first require implementation/call validity and qualified endpoint measurement, then choose the eligible shared-diagnostics model/effort/resource setting with best baseline endpoint performance under a declared uncertainty/tie policy; unresolved superiority between settings should trigger more development or a conservative tie policy rather than an invented winner. Model settings are allowed to be refined in development, but the full candidate history and new pre-call declarations remain visible. Method-reuse performance is reported regardless of whether it ties, exceeds or falls below the architecture candidate.

This comparison will resolve open scientific risks: whether the legacy renderer already saturates the complete-answer endpoint; whether B4's apparent benefit depends on baseline language choices or missing helper discovery; whether private treatment contracts contain public semantics missing from the agent prompt; whether higher effort/resource settings change quality or only completion; whether same-family annotation errors distort baseline setting selection; and whether the proposed comparator matches the paper's intended claim. A successful restricted comparison alone supports a bounded architectural-interface statement. It does not establish superiority over the unrestricted full-method reuse agent, unique physical-cause diagnosis or all repository/tool-agent designs. Keeping the reuse condition visible is essential to that interpretation.
