# Scenario diversity design v2 — prospective development

This is a source-supported expansion proposal, not a new registry or experimental freeze. It inspects generator/registry metadata and platform/collector source, without reading response answers, launching captures or changing existing sources/declarations. All new scenarios remain development until a separate prospective protocol is frozen. No sample ceiling, final N or outcome-based family selection is proposed.

## Present population and actual support

`generate_roboboat_population_v1.py` cycles six labels: nominal-turn, wide-turn, deep-turn, curved-stem, shallow-turn and direct-goal. Registry 42001 contains 12 candidate geometries/24 tolerance-variant rows, two geometries per label; 42003 contains 24/48, four per label. These are registry counts, not counts of completed/valid observations. Both retain the scene-default initial state. Five labels vary south-stem/semicircle/north-stem route parameters around a single dock approach, while direct-goal uses NavigateToPose. Requested goals vary within a .30 m square around (0.8641434,-27.586906) and yaw pi/2 ±.10 rad. The public berth remains centered at (0.8641434,-27.586906), yaw pi/2, width 2.0 m/depth 3.0 m. Current “start” coordinates (-2.2768,-5.2) are a hardcoded approximate path anchor, not a declared physical start-pose draw. Stem/path yaw is not a measurement of boat initial heading.

The source supports the following distinctions:

| Dimension | Actual source/knob | Readiness and meaning |
|---|---|---|
| Requested goal position/yaw | `CRANE_NAV2_GOAL_X/Y/YAW`; absolute NavigateToPose goal in `nav2_follow_path_fixture.py`; final supplied FollowPath pose | Implemented; keep task goal, final route pose and launch values identical |
| Explicit route poses/frame | `CRANE_NAV2_PATH_FILE`, `crane-nav2-path-v1` with `frameId`/poses | Implemented; arbitrary finite supplied route geometry is executable input, not proof of feasibility |
| Built-in path shapes | `CRANE_NAV2_PATH_SHAPE=straight/gentle-turn/s-turn`, distance, heading offset, lateral amplitude, turn angle | Implemented launcher/fixture options; the current population collector does not declare/pass these row fields and must be extended before use |
| FollowPath versus NavigateToPose | `CRANE_NAV2_ACTION_MODE` | Implemented; these are different navigation interfaces, so action mode is a declared scenario attribute |
| Controller tolerance pair | Controller extra arguments; current .2/.4 m xy thresholds, runtime readback | Implemented repeated variants within one geometry, not additional independent N |
| Docking requirement parameters | Launcher dock tolerance/speed/yaw-rate/settle/width/depth/hull arguments; public task contract | Implemented **evaluation** parameters, not physical dock/hull resizing; changing them changes the task definition |
| Initial boat pose/heading | No corresponding exposed start-pose arguments found in current worker override/collector/fixture | **Not presently implemented** as a configuration knob; needs additive initialization/orchestration support before claims of diverse physical starts |
| Seed/reset | Worker `--crane-seed`; scene reload; reset coordinator saves/restores body state | Implemented, but a new seed does not teleport or independently sample a geometry |
| Obstacles/dock/environment | Existing scene and costmap/collision behavior | Fixed supported geometry only; no new obstacle/wave/sensor/task generator is established by these sources |

`CraneWorkerOverrides.cs` sets seed, scene, transport and runtime profile; it does not set boat start x/y/yaw. `CraneEpisodeReset.cs` restores captured Rigidbody state or uses `ArticulationBody.TeleportRoot` for captured root state. That is an implementation seam, not an existing arbitrary-pose experiment API. `nav2_follow_path_fixture.py` reads initial odometry and sends one action goal; its path-heading offset rotates a requested path relative to the measured body yaw, not the body itself. Its summary records `initialPose`, but neither that field nor a changed first waypoint establishes an independently configured physical start.

The active controller profile is RegulatedPurePursuit with desired linear velocity .15 m/s, `use_rotate_to_heading=false`, `allow_reversing=false` and collision detection enabled. An arbitrary heading/approach is therefore a legitimate exploratory initial-condition challenge, not guaranteed recoverability. Do not enable reversing, alter propulsion/physics or switch controller behavior to make new families succeed without declaring a revised platform version.

## Expansion available with existing path/goal machinery

First broaden the declared route population while retaining the physical scene/default start and existing public task. Keep all six current macro-strata eligible and introduce within-stratum subtypes based on input geometry, not observed B2/B4 differences:

- **Entry direction and terminal tangent:** vary the final approach through the available water corridor rather than always using a dock-aligned north stem. Generate smooth approach tangents at candidate offsets 0, ±.10 and ±.25 rad from dock alignment, independently of requested goal yaw. Connect back to the same public goal with a declared terminal alignment segment. These are proposed bounds requiring static footprint/scene review and development feasibility; they are not claims of valid water clearance.
- **Terminal straight-run length:** vary alignment-segment length, candidate ranges 1–3, 3–6 and 6–10 m where the existing scene permits, keeping the final goal and dwell definition fixed. This samples how much alignment distance the unchanged controller receives, without manufacturing a stopping failure.
- **Left/right approach and curvature topology:** retain current single-turn geometry; add reflected-side approaches, gentle two-bend transitions and single S-bends only in declared scene-supported water corridors. Route reflection around goal x is a mathematical proposal, not evidence the mirrored side is obstacle-free. Give valid constrained or blocked routes explicit scenario identities; do not discard them for navigation failure.
- **Path/body-heading mismatch:** use the implemented path-heading-offset concept for requested path geometry, but log actual initial body yaw separately. Label this path mismatch rather than changed physical start heading. For absolute supplied docking routes, ensure the final pose remains the declared docking goal; built-in shapes by themselves generate a relative endpoint and must not silently substitute another task.
- **Goal offsets and orientation:** stratify the existing .30 m goal-position square into central versus edge subregions, and requested orientation into centered versus signed offsets. Initially retain the current ±.10 rad range; a separate prospective development sweep can widen to ±.20 or ±.30 rad after oriented-hull/berth compatibility review. Keep physical berth dimensions/location fixed. Do not move the berth center to each sampled requested goal in the public contract.
- **Direct navigation diversity:** retain NavigateToPose goals sampled under the same public task; delivered planner geometry remains an observed runtime result, not a generator-controlled route. Treat planned path variability as descriptive evidence only, without creating a second statistical configuration identity from it.

Use tangent-consistent spline/Hermite or piecewise smooth paths, finite wrapped yaw, declared odom frame, matched endpoint and bounded waypoint spacing. Record length, minimum/maximum curvature, start-path mismatch, terminal tangent and alignment length as **input-derived** design descriptors. Current route generation assigns fixed south-stem yaw even for lateral curvature; a successor should derive route yaw consistently from geometry rather than accidentally changing a controller cue. Keep the exact successor route algorithm/version hash and regard changed generated path orientation as a documented input-design revision. Route spacing/curvature bounds should be set from public controller geometry and static feasibility work before calls, not adjusted according to which explanation method fails.

The existing platform records delivered costmaps, planner feedback and behavior-tree data, but L0–L2 packets do not thereby expose every raw stream. More complicated paths do not authorize adding hidden scene geometry or evaluator truth to either method. If additional already-recorded robot-visible diagnostics are included later, define a new shared evidence version and preserve identical availability for B2/B4, consistent with `BASELINE_INTERFACE_DESIGN_V1.md`. A new sensor or privileged truth stream is not part of this proposal.

## Physical start diversity requires an explicit successor

Distinct physical starts are scientifically useful because present route diversity leaves approach preparation and initial heading almost fixed. The preferred additive extension is a **declared initial-state setter**, rather than pretending route waypoints already supply that control. It would configure the actual boat body at scene initialization, before measurement/action exposure, using the existing body restoration seam and unchanged physics/controller/sensing. This requires a new player/source/collector version and validation; no start-position flag is claimed to exist today.

Candidate development start classes are: (a) a local water patch around the measured scene-default start; (b) independently sampled intermediate route-corridor positions; and (c) a near-approach staging patch outside the fixed berth. Determine their polygons from a static scene/footprint/water audit before draws. The coordinates of classes (b)/(c) are intentionally not invented here. For class (a), proposed exploratory offsets of ±.5–1.0 m longitudinal/lateral are only candidate bounds pending that audit. Heading should be sampled relative to the intended initial route tangent, for example aligned ±pi/12, moderate signed mismatch pi/6–pi/3, and larger signed mismatch pi/3–pi/2. A separate reverse-facing development stress can be registered, but must not imply the current nonreversing controller can recover.

The physical initialization contract should include requested/observed odom x/y/yaw, body root identity, frame transform, initial velocities, initialization time, water/reset treatment and goal/path relation. Preserve the original vertical buoyancy configuration and physical hull dimensions. Do not rotate only a child sensor or translate a visual object while leaving the authoritative physics body unchanged. `Odom.cs` maps Unity position to ROS x=Unity z, y=-Unity x and publishes body-frame twist; the bow/body correction used by `RoboBoatRosFrame` also needs validation when assigning heading. Validate yaw/pose through actual delivered odometry and the deployed frame contract rather than assuming a Unity Euler-angle conversion.

Before any new task action, require a method-blind initialization check: pose within a predeclared tolerance of the request, finite declared frame/clock, consistent body/sensor frame, no initial overlap outside an explicitly registered contact-start condition, and required telemetry/transport readiness. Define fixed warmup/zero-command handling prospectively and retain the observed initial velocity; a start setter cannot claim exact zero residual motion if the platform moves during warmup. Scene reload is the reset reference. The water reset component restores the spectral timeline but explicitly does not guarantee resetting wakes, foam/deformers or temporal presentation history; do not claim full environmental reset equivalence from the API alone.

An alternative **prepositioning maneuver** could use the existing NavigateToPose action to a staging location before the scored docking action. It would preserve the running boat physics but requires a new multi-action collector protocol: current fixture sends one goal, current event/dwell anchoring applies to that goal, and carryover velocity/water history/command state would be part of the subsequent initial condition. A staging action that fails cannot be repeatedly retried until a desirable start appears. Register the complete maneuver identity, one attempt, observed achieved start, fixed settling policy and technical failure treatment. Until this is implemented/validated, no prepositioning-start data exist. Do not pool the two initialization modes as interchangeable replicas.

## Task geometry and instrumentation constraints

`CRANE_DOCK_WIDTH/DEPTH`, hull dimensions and docking tolerances are accepted by the launcher/evaluator, but they define evaluation geometry. They do not move a physical marina collider or change the boat hull. The evaluator's rectangle is centered/oriented on its goal arguments, while the public current contract uses a fixed physical berth and perturbed requested goal. A successor must document that distinction and ensure public task/reference computations represent the intended fixed berth; an evaluator-default rectangle cannot silently redefine it. Source support for varying a numeric task field is not evidence of physically resizing a dock. Initially keep the existing 2×3 m berth, 1.063×.895 m hull, public .4 m/.35 rad/.05 m/s/.05 rad/s bounds, five-second dwell and eight-second post-result capture. Later task-parameter studies belong to a declared task revision/supporting sensitivity, with collection/export/evaluator/public contract synchronized.

Longer/shorter approach routes may change how often actions reach the existing 310-second action deadline. Timeout is an admissible navigation outcome if correctly recorded; it is not technical invalidity merely because docking did not finish. If the expanded population needs a longer deadline to answer its scientific question, establish that in development from input route lengths/controller capabilities and prospective collection constraints, then use a new protocol version. Do not lengthen only unfavorable episodes or shorten dwell/capture to hide a violation. Natural recoverable/failed outcomes stay in the bank, independent of which explanation method succeeds.

## Sampling and independence accounting

Create a new immutable namespace with its own generator seed/version, full canonical configuration fingerprint and content-bound public task/path/start specifications. Include all physically relevant input dimensions—initialization mode and pose, requested goal, route, fixed scene/platform version and controller variant pair—not just labels or filenames. Canonicalize equivalent wrapped angles and route serialization so cosmetic differences cannot manufacture a second identity. Exact replays, new method prompts/models, L0–L2 masks, annotation passes and both tolerance variants add zero independent N. A repeated execution of the same start/goal/path geometry is a replicate within its cluster, even if the physics seed changes.

The v1 generator uses `seed=41000+index` for simulation launch independently of the population sampling seed; therefore populations 42001 and 42003 reuse launch seeds for overlapping draw indices. Their sampled geometry parameters are distinct, so seed reuse alone does not prove duplicate configuration draws, but it also does not establish fresh environment replication. Preserve that provenance. A successor can derive bounded launch seeds from population/geometry identity, binding the derivation and using the same seed across paired tolerance variants. Generate fresh configuration draws for replication, not merely new row names or seeds. Shared platform/water conditions limit environmental generalization even with independent configuration sampling.

Keep the current six macro-family labels for a first route/goal expansion only if their prospectively defined distributions remain scientifically meaningful; record all new subtypes and weights within each. Physical start classes can then be crossed with route classes under a declared product distribution. For example, six route strata × three audited start classes gives 18 design cells, while the scientific estimand may remain an equal-weight six-route-family average with equal conditional start-class weights. It is not automatically the same distribution as v1. If additional route topology creates genuinely new macro-families, freeze their weights explicitly and update power simulations accordingly. More cells, configurations and fresh replication draws may be generated without an arbitrary total cap.

Independent geometry draws conditional on a fixed scene are a defensible sampling unit when starts/goals/routes are drawn independently from declared distributions and runs do not share uncontrolled carryover state. A factorial sweep around one common sampled base geometry may instead warrant one outer-base cluster with repeated subconditions; do not count every near-identical perturbation as independent merely because its continuous numbers differ. Before confirmation, specify whether each full tuple is an independent draw or a within-base perturbation, and report distance/topology similarity to explain external-validity breadth. Worker/domain/port separation and scene initialization must prevent interference between purportedly independent runs.

## Actionable development sequence

1. Register a source-only route/goal expansion using the current default start and fixed task, with precise generation bounds/static audit, immutable draws and existing tolerance pair. Do not reinterpret earlier six-family banks.
2. Build and validate a separately versioned initial-pose setter (or multi-action prepositioning collector), including actual frame/body/water/readback and method-blind technical admission checks. No capture is launched by this document.
3. Register independently sampled start/goal/route tuples across audited classes, preserving all complete technical attempts and natural task outcomes. Assess telemetry coverage, timeout rates, source/reference agreement and judging reliability before primary freeze.
4. Compare evidence informativeness and measurement reliability across **predeclared** input families; refine development bounds for physical coherence or instrumentation failures, documenting each revision. Do not choose families because B2 loses or discard valid configurations that produce ties/unknown completion.
5. Update population weights, geometry-score variance/missingness power sensitivity and replication generation before freezing any confirmatory protocol. Endpoint and strongest-fair-baseline interface remain governed separately; diversity must not change either method's evidence privileges.

The proposal leaves all sources, existing registries/declarations and outputs unchanged. It supplies no claim that a new pose/path is feasible or that any proposed family favors CRANE.
