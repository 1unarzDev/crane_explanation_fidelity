# Concurrent rendering: FPS ownership candidate

This development change addresses a concrete scaling restriction: the qualified v3 wrapper saves/restores the global compositor FPS setting independently. Overlapping wrappers could restore the previous setting while another player still needs60FPS. Live v12 collection and the queued start-pose probe retain unchanged v3 sources and their exclusive render lock.

The additive FPS lease module supplies first-acquire/last-release ownership. New v4 wrappers hold a shared lock on the existing `/tmp/crane-roboboat-population-render.lock`, so old exclusive collectors remain protected and new cooperating wrappers can overlap. A separate short transition lock serializes source-bound owner-state changes. State records the compositor instance hash, original setting and exact PID/start/nonce owners. Only the first changes FPS and only the last restores the original. Both operations verify readback while still holding their gate.

The state preserves incomplete STARTING/RESTORING transitions, lost owners/PID reuse and unexpected external setting changes. It refuses new acquisitions/restoration rather than overwriting another setting or silently discarding unresolved owners. Operational recovery requires inspecting retained state and actual compositor/process evidence; no automatic force recovery is implemented. Owned output/window/process-group cleanup remains scoped by exact nonce/session identity. Its helper functions are AST-identical to v3. No global configuration reload is added.

Twenty-five tests passed across the lease, v4 and inherited v3 wrappers. They include two actual child processes overlapping against a simulated shared FPS setting: the first release leaves60FPS, the last restores11FPS, with only two writes. Another actual child blocks behind a legacy exclusive lock before changing the simulated setting. Tests cover reverse finish order, zero original FPS, external changes, interrupted transitions, PID reuse, incompatible settings and compositor scopes, plus mocked owned handle cleanup and inherited actual disposable-process-group cleanup. These tests do not establish actual compositor or Unity concurrency.

The fixed actual compositor probe is declared under `artifacts/roboboat-parallel-render-ownership-v14-001/`. Two child wrappers each create a nonce-owned empty output/workspace, hold for5s and clean up. There is no Unity, ROS, study recording or independent N. Exact session83176 (child PIDs1060359/1060360) is queued behind the existing legacy exclusive holders, with no global mutation while waiting. Its primary engineering checks require both clean outputs, overlapping active leases, one nonlast and one last release and the same recorded original FPS. It does not compare an unrelated later global read, which could occur after another legacy job acquires its own exclusive lock.

Even a passing empty-output probe does not qualify actual concurrent Unity window placement, sensing, water physics, navigation, complete action traces, population failure rate or a paper result. Those operational checks precede adoption for scalable data collection. New collection orchestration must allocate unique configuration identities and separate ROS domains/ports and must not hold an exclusive batch render lock around cooperating v4 children: doing so would block their shared locks. It still needs a separate per-configuration/worker allocation mechanism to prevent duplicate collection. Existing declarations stay unchanged.

Confirmation remains unfrozen; zero method endpoint pairs are scored. The live physical batch continues independently. The intended outcome remains sufficiently powered B4-vs-strongest-fair-B2 superiority on complete supported diagnostic answers, with qualified model judges/source audits and feasible fresh replication, not software readiness.
